# RULES.md

> Agent behavior rules. Generic and reusable without changes between projects.
> Do not edit this file — if a project needs additional rules,
> add them to the specific constraints section of `ROLE.md`.

---

## Rules

**1. Never assume — verify against the actual source.**
Before answering about the state of a document, a decision, or a requirement,
read the actual document. The memory of previous conversations does not replace
reading the file.

**2. Never resolve a discrepancy silently.**
If two documents contradict each other, or if a user request contradicts
a document of higher authority: point it out explicitly and wait for instruction.
Do not choose an interpretation and proceed without warning.

**3. Mandatory upward traceability in the hierarchy.**
Every edit or generated content must be justifiable by tracing back to a
document of higher authority in `HIERARCHY.md`. If no traceability is possible,
point it out before proceeding.

**4. Every correction or lesson learned is documented — not just mentioned.**
If an error is detected or something is learned that improves the process, log it
in `IMPROVEMENT_LOG.md` in the same session it occurs. Mentioning it in the
chat is not enough — the chat does not persist between sessions.

**5. A single place for each type of information.**
Do not manually duplicate information that can be referenced. If the same data
lives in two places, one of them will inevitably become outdated.

**6. Ask before destructive or irreversible actions.**
Deleting, archiving, overwriting, or restructuring documents requires
explicit confirmation from the user, even if the request seems to imply it.

**7. Distinguish proposal from decision.**
When the agent suggests something, make it clear: "this is my suggestion".
When something has already been agreed upon, reference it: "this is what we decided on [date/session]".
Do not present suggestions as if they were finalized decisions.

**8. When closing a session, document the reasoning — not just the result.**
In `LOG.md` it must be recorded why decisions were made, not just what was done.
The reasoning is what is most easily lost between sessions and most valuable
for reconstructing context.

**9. Explicitly name what was read when starting a session.**
Upon completing the start ritual, indicate to the user which files were read
and what the current state of the project is according to `CURRENT_STATE.md`.
This prevents operating on incomplete context without knowing it.

**10. When correcting an obsolete convention, find ALL instances.**
If a rule, name, format, or convention changed and appears in multiple documents,
find and correct all occurrences before considering the correction closed.
Correcting only the most visible instance is not enough.

**11. After renumbering or reordering sections, review cross-references.**
Any reference like "see section N" or "according to point X" becomes
automatically outdated when a document is reordered. Always review them
— they are not visible in a superficial read.

**12. The consistency ritual can be invoked on demand as a comprehensive check.**
Do not wait to edit a document to verify consistency. If the user
requests it — or if the agent detects a risk of divergence between documents —
execute ritual §2 of AGENTS.md on the entire project.

**13. Search and Navigation (Lazy Loading).**
To locate files or understand the project structure, do not perform blind explorations. Consult `project_tree.md` first (in the root) to see the full repository tree, and the `index.md` files (in each folder) to get the semantic context of the documents.
